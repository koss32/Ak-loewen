## Concrete issues / minimum recommendations
1. **Indexing is fail-closed everywhere, with no launch switch.** Vercel sends `X-Robots-Tag: noindex, nofollow` globally (`vercel.json:16-22`); generated robots disallows all (`build.js:10`); localized/legal HTML hard-codes `<meta name="robots" content="noindex,nofollow">` (`src/render.js:41`); root entry does likewise (`src/entry.js:1`). Add one explicit owner-controlled `INDEXING_ENABLED` (default false), and only when true align header, robots, root/localized meta, canonical origin and a sitemap; keep preview false. Do not activate here.
2. **Preview ops guard is stale for Release 6.** `server/telegram-ops.js:3-7,36-54` hard-codes origin `ak-loewen-bot-preview.vercel.app`, branch `release-3`, and privacy URL. `runWebhook` would set/check that exact preview webhook (`:224-229`). On a Release-6 deployment this makes checks/mutations fail unless platform metadata is incorrectly spoofed. Update only under owner-approved preview verification, then check actual Vercel branch/origin; no remote check was run.
3. **Web form bypasses bot privacy readiness.** `build.js:6` and `api/trial-requests.js:10` gate delivery only on `FORM_DELIVERY_ENABLED`; the form endpoint never checks `PRIVACY_URL`, publication status, or consent version, unlike bot readiness (`server/bot-config.js:65-86`). Minimum: gate form delivery on the same published privacy/version conditions, or prove equivalent deployment guardrails before enabling.
4. **PUBLIC_ORIGIN slash/malformed pitfall.** Bot validation accepts one trailing slash (`bot-config.js:20-27`), but form API compares `Origin` literally (`api/trial-requests.js:12-13`) and build concatenates `${origin}/${locale}` (`build.js:8`, `render.js:39`). A trailing slash can 403 browser form POSTs and produce `//de/` canonicals. Set exact HTTPS origin without slash in each Vercel scope; ideally share normalization/validation. Form API also constructs Redis without the bot branch's HTTPS URL validation (`trial-requests.js:15-20`); validate HTTPS and a complete URL/token pair before use.
5. **Local safety differs from Vercel.** `server.js:10-13` enables real local Telegram form delivery whenever legal source status plus bot token/chat ID exist, ignoring `FORM_DELIVERY_ENABLED`; local server only sets two security headers (`:18`), while Vercel adds frame, robots and permissions headers. Keep real secrets absent locally; treat local checks as non-deployed.

## Security / persistence / auth
Vercel headers provide nosniff, strict-origin referrer, DENY framing, noindex and restrictive camera/mic/location policy (`vercel.json:18-22`), but no CSP or HSTS (HSTS is a production HTTPS recommendation). Bot production construction requires Redis (`bot-runtime.js:49-56`); Upstash variables are preferred, KV variables are compatibility aliases, and the `{akbot}:` prefix is used for generation/state CAS snapshots. State/outbox/request retention is approximately 30 days; form ledger uses separate `trial:req:*`/rate keys (hosted-trial). No Redis health or schema was verified remotely.

Webhook auth requires enabled flags, strong independent secret, exact configured host, JSON content type, and Telegram secret header (`telegram-webhook.js:48-57`). Staff actions require the configured negative group ID and current `getChatMember` verification (`telegram-bot.js:26,95,111-123`); allowlist requires IDs, group-members mode requires bot-admin readiness. Worker/reminders and bridge remain disabled/future (`.env.example:13-28`); no scheduler is required or enabled.
